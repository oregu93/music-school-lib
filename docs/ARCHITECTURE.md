# Архитектура MLC

## 1. Назначение

MLC — веб-приложение для работы библиотекаря с электронным каталогом. Каноническая рабочая копия каталога хранится в серверной базе D1. Клиент предоставляет поиск, просмотр и редактирование карточек, выдачу/возврат, инвентаризацию, экспорт и поддержку временной работы при нестабильной сети.

## 2. Компоненты

### Front-end

Основной интерфейс находится в `app/catalog-client.tsx`.

Он отвечает за:

- каталог и поиск;
- бесконечную подгрузку записей;
- desktop- и mobile-представления;
- карточку экземпляра;
- редактирование и добавление;
- выдачу/возврат;
- инвентаризацию;
- пользовательские статусы синхронизации.

UI-компоненты находятся в `components/ui/`.

### Worker/API

Серверная логика расположена в `src/worker/index.ts`.

Cloudflare Worker:

- обслуживает API;
- проверяет серверную сессию;
- выполняет поиск;
- читает и изменяет D1;
- применяет правила конкурентного редактирования;
- обрабатывает выдачу/возврат и инвентаризацию;
- формирует экспорт;
- выполняет OAuth callback и управление сессиями.

### База данных

Production использует Cloudflare D1 (SQLite).

Ключевые сущности:

- `catalog_records` — карточки каталога;
- `loans` — выдачи и возвраты;
- `audit_log` — аудит изменений;
- `app_users` — разрешённые пользователи;
- `auth_sessions` — серверные сессии;
- `sync_operations` — идемпотентность/история синхронизации;
- `inventory_sessions`, `inventory_events` — инвентаризация.

Миграции находятся в `migrations/`.

## 3. Пользовательский маршрут

Основной пользовательский адрес:

```text
https://mlc-vercel-access.vercel.app/
```

Схема:

```text
браузер
  |
  v
Vercel access gateway
  |
  v
Cloudflare Worker
  |
  v
production D1
```

Vercel не хранит отдельную базу и не содержит отдельной копии каталога. Его задача — предоставить рабочий внешний origin и корректно проксировать обычные и OAuth-маршруты.

Технический прямой адрес Worker:

```text
https://music-school-library.oregu93.workers.dev/
```

Он сохраняется как backend/резервный маршрут, но пользовательские ярлыки и инструкция должны указывать на Vercel.

## 4. Авторизация

Используется Yandex OAuth 2.0:

- Authorization Code Flow;
- PKCE S256;
- `state`;
- серверный callback;
- whitelist в `app_users`;
- роли `admin` и `librarian`;
- HttpOnly session-cookie;
- хранение server-side session state в D1.

OAuth access token Яндекса не сохраняется как пользовательская сессия MLC.

Подробности: [OAUTH.md](OAUTH.md).

## 5. Поиск

Поиск выполняется сервером. Для повторно используемых текстовых полей хранится нормализованное поисковое представление.

Пользовательский основной номер — `inventory_number`.

`db_number` сохраняется как secondary/legacy identifier.

На мобильных устройствах реализован отдельный focused-search: при открытой экранной клавиатуре результаты занимают доступную видимую область над строкой поиска. Для расчёта доступного viewport используется `VisualViewport` с CSS fallback на динамические viewport units.

## 6. Offline/outbox

При временной потере сети изменяющая операция не должна silently теряться.

Клиентская очередь хранится в IndexedDB:

```text
pending -> syncing -> success / conflict / failed
```

При восстановлении связи pending-операции повторяются автоматически. Каждая синхронизируемая операция имеет стабильный `operation_id`; серверная логика поддерживает идемпотентное повторение.

В обычной онлайн-работе пользователь видит компактный статус «Синхронизировано». Ручная кнопка отправки появляется только при наличии ожидающей очереди.

Текущая реализация outbox покрывает изменяющие библиотечные операции. Полная автономная локальная реплика всего каталога остаётся отдельным направлением дальнейшего PWA/offline hardening.

## 7. Конкурентное редактирование

Изменяемые карточки имеют `revision`. Клиент передаёт `baseRevision`, сервер не должен молча перезаписывать более новую версию.

Бизнес-конфликты (например, несовместимые операции выдачи) отклоняются сервером.

## 8. Staging и production

Для staging и production используются разные Worker/D1-конфигурации.

Перед deployment выполняется identity check. Стандартный путь:

```text
изменение кода
 -> pnpm launch:check
 -> deploy staging
 -> acceptance
 -> backup при необходимости
 -> deploy production
 -> production smoke/acceptance
```

## 9. Переносимость

Cloudflare и Vercel — текущая инфраструктура, но не должны определять бизнес-модель приложения.

Ключевые принципы:

- данные — обычная реляционная схема SQLite-уровня;
- клиент — стандартный React/TypeScript;
- HTTP API — без обязательной зависимости от Cloudflare client SDK;
- миграции и экспорт версионируются;
- возможен перенос на другой cloud или обычный Linux-hosting при реализации совместимого API/SQLite слоя.

См. [ARCHITECTURE_RULES.md](../ARCHITECTURE_RULES.md).
