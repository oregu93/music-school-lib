# Импорт и проверка каталога

## Назначение

Импорт нужен для первоначальной загрузки или контролируемого обновления каталога из подготовленного Excel/CSV-источника.

Production D1 является рабочей системой записи. Исходные таблицы рассматриваются как резервный/импортный источник и не должны автоматически перезаписывать production.

## Защита исходных данных

- неизменяемая резервная копия исходного каталога не редактируется;
- рабочая копия для преобразования хранится отдельно;
- подготовленные SQL/CSV/JSON с реальными библиотечными данными не отправляются в Git;
- destructive import требует отдельного backup и явного подтверждения.

## Историческое соответствие идентификаторов

В исходной выгрузке MARC/Excel использовалось соответствие:

- исходное поле «Инвентарный номер» -> `db_number` («№ записи в БД»);
- исходное поле «Штрихкод (852$p)» -> `inventory_number` («Инвентарный номер» в MLC).

Поэтому `db_number` считается legacy/source identifier, а `inventory_number` — основным пользовательским номером экземпляра.

## Проверка локального источника

Проект содержит Python-скрипты для проверки структуры и подготовки импорта.

Перед загрузкой необходимо проверить:

- количество записей;
- обязательные столбцы;
- контрольные поля;
- пустые значения в идентификаторах;
- допустимые дубли `inventory_number`;
- отсутствие неожиданной потери строк.

Конкретные контрольные количества относятся к соответствующей версии source-файла и не должны быть захардкожены как вечный инвариант.

## Подготовка импорта

Пример:

```bash
python scripts/catalog_to_sql.py ../outputs/library_catalog_complete.xlsx --check-only
```

Подготовка SQL:

```bash
python scripts/catalog_to_sql.py ../outputs/library_catalog_complete.xlsx --output private-data/library.catalog-import.sql
```

Файлы из `private-data/` не должны попадать в Git.

## Staging-first

Любой новый импорт сначала проверяется на staging/временной базе.

После загрузки сверяются:

- `COUNT(*)`;
- несколько известных карточек;
- поиск по инвентарному номеру;
- поиск по автору/заглавию;
- наличие legacy-полей;
- отсутствие неожиданных duplicates/loss.

## Production

Production import выполняется только после:

1. свежего D1 backup;
2. PASS staging validation;
3. явного выбора production environment;
4. сверки количества строк и контрольных карточек.

Опция очистки/замены существующих данных допустима только как отдельная controlled operation после резервного копирования.

## Git и приватность

В Git хранятся:

- код преобразования;
- миграции;
- документация;
- тестовые синтетические fixtures.

В Git не хранятся:

- полный рабочий каталог;
- production SQL dump;
- персональные данные;
- реальные session/auth данные.
