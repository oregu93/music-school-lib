# MLC — электронный каталог библиотеки музыкальной школы

MLC — самостоятельное веб-приложение для работы с библиотечным каталогом. Это не конструктор сайтов и не готовая библиотечная CMS: интерфейс, API и логика работы разработаны в рамках проекта.

Система используется библиотекарем для поиска и просмотра фонда, добавления и редактирования карточек, выдачи/возврата, инвентаризации и экспорта данных. Рабочая база хранится на сервере; исходные Excel/CSV-файлы используются как резервные и импортные источники.

## Текущий технологический стек

- **Front-end:** React + TypeScript + Vite.
- **UI:** собственные React-компоненты на базе Base UI / shadcn-подхода и Tailwind CSS.
- **Back-end/API:** Cloudflare Worker.
- **База данных:** Cloudflare D1 (SQLite).
- **Авторизация:** Yandex OAuth 2.0 Authorization Code + PKCE, серверные сессии.
- **Исходный код и история изменений:** GitHub.
- **Пользовательский адрес:** Vercel access gateway, проксирующий production Cloudflare Worker.
- **Подготовка и контроль данных:** Python, pandas/openpyxl и служебные скрипты проекта.

## Рабочая схема

```text
браузер библиотекаря / телефон
            |
            v
https://mlc-vercel-access.vercel.app/
            |
            v
Vercel access gateway
            |
            v
Cloudflare Worker (API + статический клиент)
            |
            v
Cloudflare D1
```

Vercel не содержит отдельной копии каталога и не является второй базой данных. Он используется как внешний пользовательский шлюз. Канонические данные находятся в production D1.

Прямой адрес Worker сохраняется как технический/резервный маршрут:

```text
https://music-school-library.oregu93.workers.dev/
```

## Основные функции

- поиск по каталогу и фильтрация;
- бесконечная подгрузка записей порциями;
- фиксированный заголовок таблицы;
- сортировка по автору/заглавию и по времени изменения в обоих направлениях;
- отдельный мобильный режим поиска над экранной клавиатурой;
- полная карточка экземпляра;
- авторасширяемые текстовые библиографические поля;
- добавление нового экземпляра с возможностью взять похожую карточку за основу;
- редактирование;
- отметка «Проверено»;
- выдача и возврат с журналом операций;
- восстановимое удаление и корзина;
- инвентаризация;
- экспорт полного каталога;
- локальная очередь несинхронизированных изменений при временной потере связи;
- автоматическое повторение ожидающих операций после восстановления связи;
- аудит изменяющих операций.

## Идентификаторы

Основной пользовательский идентификатор экземпляра — `inventory_number` («Инвентарный номер»).

`db_number` («№ записи в БД») — вторичный legacy-идентификатор исходной системы. Он сохраняется в данных и API для совместимости, но не является основным номером экземпляра.

Инвентарные номера в исторических данных могут повторяться, поэтому они не имеют ограничения UNIQUE. При нескольких совпадениях интерфейс требует явного выбора записи.

## Окружения

Используются три уровня:

1. **local** — локальная разработка;
2. **staging** — проверка изменений до выпуска;
3. **production** — рабочая версия библиотекаря.

Путь изменений:

```text
local -> staging -> production
```

Production не используется как среда разработки.

## Проверка перед выпуском

Основная команда:

```bash
pnpm launch:check
```

Она выполняет тесты базы/миграций и контрактов, TypeScript typecheck и production-like сборку клиента/Worker.

Развёртывание:

```bash
pnpm deploy:staging
pnpm deploy:production
```

Скрипты выполняют проверку идентичности выбранного окружения перед deployment.

## Защита данных

В репозиторий не должны попадать:

- `.dev.vars`, секреты и session-токены;
- рабочие Excel/CSV/SQL-экспорты с библиотечными данными;
- персональные данные сотрудников;
- резервные копии production D1.

Такие файлы исключаются из Git и хранятся отдельно.
